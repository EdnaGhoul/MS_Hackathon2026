# Photograph pipeline — discovery, capture, verification

The customer asks for photographs and judges the report on them first. This is
the part of the skill most likely to under-deliver, so it is the part with the
most machinery. Read it before Phase 1.

> **Priority order: GET THE PICTURE first, the best version of it second, place
> it small third.** A verified face captured badly and placed at thumbnail scale
> beats an empty row.

## Scope — what may be shown as a picture

| May be shown | May NEVER be shown |
|---|---|
| A photograph of the subject | A video thumbnail, still frame, podcast cover, channel banner, episode card |
| A page screenshot where the PAGE ITSELF is the finding (a wrong title rendered on screen) | A logo, a stock illustration, a generated or synthesised likeness |
|  | A decorative screenshot of a bio page or team listing |

Video and audio items are **text rows** in `sections.av_items`. If an A/V item
carries a finding — the subject does not appear, it is branded to the host, no
footage of them exists anywhere — state that finding in words. Earn it: sample
frames across the runtime rather than judging the cover art.

## Phase 1 — discovery is PARALLEL and STATELESS

`host-search_images` is the discovery tool, and using it is a deliberate
reversal of v1. Two to three queries per subject — `"<name>"`,
`"<name> <org>"`, `"<name> <role or event>"` — return `source_url` (the
original), `page_url`, `width`, `height`: exactly the candidate list. Add page
captions and "Pictured:" lines from `web_fetch`.

v1 banned that tool to protect accuracy, because discovery metadata names a
picture without showing it. v2 keeps the accuracy guarantee where it belongs —
at **verification** — and unlocks the stateless discovery a roster needs.
**Nothing is published from discovery metadata.** Nothing reaches a document
until it has been rendered in the browser, cropped and visually verified.

Write every candidate into `assets.json` with `state: "candidate"`. Do not cap
the list; `plan_capture.py` applies the budget.

## Phase 2 — capture is SERIAL and BROWSER-EXCLUSIVE

The browser is a single session with one globally-selected tab. Capture is a
stateful two-step — navigate to the image, *then* screenshot — so any sibling
agent that navigates in between destroys the attempt. Measured on a ten-person
roster with ten concurrent agents: roughly **one screenshot in six** landed on
the agent's own page, and several returned a *different subject's* face; the
same assets captured 5-of-5 in a single-subject run days earlier.

So: **one capture agent per subject, dispatched one after another.** Never two
alive. Each gets a fresh context and a fixed queue of at most `capture_budget`
items, generated by `plan_capture.py --brief <slug>` — which is how the rules,
the queue and the organisation's image-server pattern reach it intact. A brief
that says "capture a portrait of each person" makes one-per-person the ceiling;
the generated brief names the rule and the queue instead.

Append `&run=<slug>-<asset>-<tier>` to every navigation URL and check
`browserState.url` contains it. If it does not, log `tab_mismatch` and retry
once — contention must be visible, never silent.

## The ladder — when a rung fails, drop to the next one

Always start at A+/A. `log_attempt.py --next` returns the next rung, so the
agent never decides to give up; `exhausted` is only reachable after all five
rungs are logged.

| Tier | What it is |
|---|---|
| **A+** | Ask the image server for a bigger rendition (see the CDN table below) |
| **A** | The original image URL, rendered alone filling the viewport |
| **B** | The search detail view — click **Full screen** first, it roughly doubles the preview |
| **C** | The hosting page, scrolled so the image is in view, cropped with `--box` |
| **D** | A results-grid tile. The worst source and the final rung — but a Tier D crop of a verified face still goes in the report |

| What happened | What to do next |
|---|---|
| The CDN returns 403 / hotlink-protected | Tier B — the search index still holds a copy |
| The hosting ARTICLE is paywalled | **Test the image file anyway.** Paywalls gate article text; the picture usually sits on an open path |
| The platform requires login (LinkedIn, Instagram) | Tier B — the page is walled, the picture is not |
| The image URL cannot be discovered | Tier C |
| Everything above refused | Tier D |
| The face is not identifiable at any size reached | `unverifiable` — a text row, with the reason |
| It is not a photograph of the subject | `not_photo` — scope rule |

### Tier A+ — the organisation's image server

Most corporate sites serve portraits through a dynamic image server that accepts
a width parameter, so the rendition a page embeds is rarely the largest
available. **Resolve the pattern ONCE for the organisation and write it into
`run.json`**, so every subject benefits — not just whoever discovers it.

| CDN | Tell-tale in the URL | Ask for more |
|---|---|---|
| Adobe Scene7 / Dynamic Media | `scene7.com/is/image/…`, `$PRESET$` | replace the preset with `?wid=2400` |
| Cloudinary | `res.cloudinary.com/…/upload/w_400/` | raise or drop the `w_` segment |
| Imgix | `?w=600&h=400` | raise `w` / `h` |
| WordPress | `photo-1024x683.jpg` | try the un-suffixed `photo.jpg` |

Observed: the same asset came back 1280×929 for a run that discovered the
pattern mid-flight and 2000×1452 for a run that knew it up front. Key
conventions drift inside one library (`firstname-lastname`, `l-turley`,
`e-scanlon-2025-2`, `marguerite-larkin-cfo-executive-director`) — record the
exceptions with the pattern.

That a whole leadership team is served from **one** image library is itself a
finding: many result URLs resolving to one photograph is ONE asset, a consistency
strength and a variety weakness — never a reason to pad the gallery.

## When the failure is OURS, say so

The reason line a reader sees is generated from the attempt log, so the log has
to distinguish a publisher refusing from a tool breaking. Two states exist for
exactly that:

| State | Means | What the reader is told |
|---|---|---|
| `exhausted` | All five rungs were walked and every one reached a host and failed | "every route to the file refused: …" with the rungs named |
| `browser_unavailable` | The browser session stopped responding | "the browser became unavailable during this run, so this photograph was never tested against its host" |
| `unresolved_address` | No image address was ever resolved — only the page | "no address for the image file could be resolved … so there was nothing to retrieve" |

`tab_mismatch` and `browser_unavailable` attempts **never advance the ladder and
never appear in an `exhausted` reason**. A dead tool reported as "every route
refused" tells a Corporate Affairs team the press will not serve them images —
a false finding, and worse than no finding.

```bash
python scripts/log_attempt.py --run <dir> --subject <slug> --browser-down   # close the queue as retryable
python scripts/plan_capture.py --run <dir> --refill <slug>                  # re-spend a failed budget
```

## Resolve the address before walking the ladder

Tiers A+ and A open an IMAGE file. A candidate carrying only its page URL has
nothing to open, so all five rungs will "fail" without a single request ever
testing a host. `plan_capture.py` flags these (`address_unresolved`) and the
capture brief lists them first. Resolve by opening the page, or by running the
image search in the browser and reading `mediaurl=` (the true original) and
`expw=`/`exph=` (native size) from the browser URL after clicking the tile.

## Ranking: the canonical headshot is pinned

The employer-controlled headshot is the picture an ordinary searcher meets
first, and it is the one most certain to be retrievable — so it is rank 1 and a
budget can never cut it. Independence from the employer still orders everything
below it. (Ranking on independence alone once spent the whole budget on press
portraits and left the corporate headshot as a text row.)

## Verification — the accuracy guarantee

After cropping, `view` the PNG and record the decision:

```bash
python scripts/set_state.py --run <dir> --subject <slug> --asset asset-01 \
  verified --matched-against "asset-02 corporate headshot; the caption names the subject"
```

- The matching baseline is the highest-ranked asset whose caption names the
  subject on an employer-owned or editorial page.
- **Name-collision subjects** — flagged automatically when `first_impression`
  holds any `wrong-person` result — need **two independent caption-named assets
  to agree** before a third is accepted.
- The verification statement is copied into the figure caption verbatim.
- There is no silent drop: `unverifiable` and `wrong_person` are states with
  reasons, not deletions.

## Budgets, and what they do and do not limit

`capture_budget` (default 8) limits **attempts**, never display: every verified
capture is shown. Assets beyond it become `budget_capped` with the reason
"attempt budget of N reached; listed as text". Hitting
`max_attempts_per_subject` or `max_minutes_per_subject` moves the remaining
queue to `budget_exhausted` — visible in the report's closing note and in chat,
never silent. A user who asks to "show every photograph" raises the budget.

## Quality decides placement, not inclusion

`image_qc.py` reads the manifest, reconciles files against it in both
directions, and writes `placement_mm` back (80 mm uniform, or the image's own
ceiling where smaller). Sharpness is advisory. What FAILS: a verified asset with
no file, a file with no manifest row, a recorded upscale, a non-terminal asset.
Never enlarge, and never report tiers, pixel counts, sharpness or gate results
to the reader — that is production detail.

## If the browser is unavailable

Publish **no pictures at all** and say so plainly in the limitations, with the
candidate list intact as text rows. If `host-search_images` is disabled in the
tenant, fall back to browser Bing-image-grid discovery with the same manifest
contract, and state that in the limitations too. Do not claim a service is
temporarily down.
